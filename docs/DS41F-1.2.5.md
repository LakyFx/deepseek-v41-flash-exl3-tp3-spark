# DS41F 1.2.5 — the production K2a recipe

**1.2.5 is the public name for the currently running 1.2.4k2a build.** It is not
a new optimization or a retuned benchmark configuration. All three running
executables, both chat-template roles, static inference settings and gateway
module hashes were freshly compared before publication. See the
[production parity receipt](../results/20261023-1.2.5/PRODUCTION-PARITY.json).

## Build, prepare and launch

Follow [1017 weight preparation](DS41F-1.2.0.md),
[host requirements](HOST-ENVIRONMENT.md) and [TP3 installation](TENSORFOLD-INSTALL.md).
Use the pinned Zig **0.17.0** toolchain and a fresh source/build/output directory.

```sh
python3 tensorfold/extract.py --out /srv/ds41f-build-1.2.5
python3 tensorfold/variants/build.py build \
  --recipe k2a --build-root /srv/ds41f-build-1.2.5 \
  --out /srv/ds41f-built-1.2.5 --zig zig
```

The 1,137-file source tree is checked against the exact sealed K2a manifest.
Existing frozen kernels and weights remain unchanged. `BUILD.json` binds the
actual local head/follower executables to that source identity.

Install independently on **each of the three ranks**, retaining older releases:

```sh
python3 tensorfold/variants/build.py install \
  --built /srv/ds41f-built-1.2.5 --runtime /srv/ds41f-runtime --variant 1.2.5
```

On the **head only**, prepare the qualified chat-template metadata overlay:

```sh
python3 tensorfold/prepare_template.py --runtime /srv/ds41f-runtime
```

This creates `weights/models/TF351-1017-1.2.5` with links to existing model
metadata and the exact direct-output template. It refuses an existing output.
It does not modify original model files or weight bytes. Keep this recipe
checkout available because the overlay links to its immutable template.

Set your topology in `tensorfold/cluster.local.json` using the existing example.
Print each rank command first, then coordinate startup in your maintenance window:

```sh
python3 -m tensorfold.launch --config tensorfold/cluster.local.json --variant 1.2.5 --rank 0
python3 -m tensorfold.launch --config tensorfold/cluster.local.json --variant 1.2.5 --rank 1
python3 -m tensorfold.launch --config tensorfold/cluster.local.json --variant 1.2.5 --rank 2
```

`--run` verifies matching source/build receipts, executable hashes, the
rank-specific template, pinned model revision, rank/Engram artifacts and RoPE
capacity before executing the selected local rank. The head uses the overlay;
followers use the original metadata. Add `--benchmark` only for a closed,
exclusive loopback benchmark window. Installation does not alter existing services.
For automatic startup, select `TF_PROFILE=1.2.5` in your own environment for the
provided `tensorfold/tp3@.service` after successful local qualification. Coordinate
all ranks and allow their existing 1,800-second startup timeout. The launcher
does not invent your topology or rewrite boot configuration.

## What changed after CDEF / 1.2.4

1. **K2 foundations:** retain live overlapping prefix state instead of blindly
   choosing a placement that conflicts with useful retained snapshots; expose
   speculative proposals/acceptance per depth; include the novelty signal in
   repetition protection. These observations do not retrain the model or prove
   that every workload becomes faster. The original K grammar integration is absent.
2. **K2a cache pressure:** an entry confirmed physically dead is reclaimed first.
   Borrowed resume entries stay protected. Selection among valid entries retains
   the existing superseded/LRU policy; incompatible with one prompt does not mean dead.
3. **Reuse diagnostics:** successful restores earn observations; deduplication
   does not masquerade as a restore. Additional state is 40 CPU bytes per entry.
   An alternative eviction score is evaluated in shadow only; it never picks
   actual victims. The 3 GiB GPU snapshot budget remains unchanged.
4. **KV reporting:** ignore empty active intervals in the occupied-union gauge.
   This corrects the reported count rather than allocating more memory.
5. **Vision lifecycle:** native generation identity, persisted dispatch IDs,
   finite deadlines, cancellation receipts, protection against late dispatch,
   bounded reconciliation and no automatic regeneration of uncertain jobs.
6. **Prompt memory:** emit template output directly rather than repeatedly
   concatenating and copying the growing history string. This is not history
   compression. Both template forms matched on 192 Python output cases and 192
   native renderer/tokenizer cases. The tested long fixture saved about
   0.852 GiB peak RSS per local process; that is a CPU counterfactual, not a
   guaranteed production-RAM or TPS gain for every conversation.

Head switches `TF_K2A_DIAGNOSTICS=1`, `TF_K2A_PRUNE_DEAD=1` and the production
repetition-guard setting `TF_LOOP_DRY_WINDOWS=10` are explicit in the profile.
Setting the diagnostics switch to zero disables extra reuse/shadow diagnostics;
the second restores legacy pressure eviction. They are initialization settings,
not live gateway toggles. The gauge fix remains active either way.

## Gateway and vision

Install the updated optional [gateway package](GATEWAY.md) separately. Use your
own secret, upstream URL and private state directory. Its production defaults are
two concurrent image requests, additional accepted requests queued, 1,800-second
queue allowance, 3,590-second job deadline and 60-second cancellation grace.
Standalone MEDIUM images receive 3,072 reasoning tokens plus **32,768 final-answer
tokens**, 35,840 total. Agent requests with tools/history keep their own budgets.
The native control endpoint `/internal/vision/control` must be reachable through
the configured vision upstream. Control failure stops image dispatch before
inference; socket closure is never accepted as a termination receipt.
