# 1.2.7 — adaptive KV retention for real agent workflows

**1.2.7 is the production name for the exact deployed X4 payload.** It combines
the established 1.2.6 engine and speculative controller with the ABCD runtime
changes and the X1–X4 prefix-retention work. The promotion does not change model
weights, quantization, sampling, native executables or the vision gateway.

The [machine-readable profile](../tensorfold/profiles/1.2.7.json) pins the full
48-row cost prior, template hashes, weight revisions and runtime flags. R48 is
neither 48 drafts per request nor a constant draft count: the existing controller
chooses proposals and the shared verification allocation within that ceiling.

The 3 GiB checkpoint budget and 7M physical KV pool serve different purposes.
Valid SWA/native states, namespace and an unchanged token prefix are all needed
for reuse. Free KV alone does not make every old conversation restorable.

## What the new controller does

It observes **verified prefix returns**, their spacing in request events, and
successful prefill costs. Under memory pressure it compares a bounded number of
legal placement alternatives, preferring useful reusable states while keeping
the original compatibility and copy limits. A short one-off task can age out;
a genuinely returning short task can gain protection. Large reusable work
contexts keep explicit safeguards. There are no client-name or cron-specific
priority rules and no promise to retain an abandoned context indefinitely.

X4 adds a narrowly bounded rescue for recently verified continuations up to
32K. It can relax the fractional extra-KV-loss allowance within the same absolute
32K ceiling, provided it does not introduce new proven long-context victims
against the original and independently reconstructed X3 choices. Rejection
diagnostics identify the first failed condition.

The prefix learner and speculative learner are separate CPU policies. Neither
trains the LLM. Their online state is process-local and restarts from its priors
after a native restart. [Exact progression and limits](X1-X4-DEVELOPMENT.md).

## Build, install and launch

Use the unchanged [1017 weight preparation](DS41F-1.2.0.md),
[host environment](HOST-ENVIRONMENT.md) and [TP3 installation](TENSORFOLD-INSTALL.md).
The pinned toolchain is Zig **0.17.0**. Use new build/output directories; all three
ranks must run the same source recipe and matching kernels.

```sh
python3 tensorfold/extract.py --out /srv/ds41f-build-1.2.7
python3 tensorfold/variants/build.py build --recipe v127 \
  --build-root /srv/ds41f-build-1.2.7 --out /srv/ds41f-built-1.2.7 --zig zig
python3 tensorfold/variants/build.py install --built /srv/ds41f-built-1.2.7 \
  --runtime /srv/ds41f-runtime --variant 1.2.7
```

On the head only, prepare the exact direct-output metadata overlay:

```sh
python3 tensorfold/prepare_template.py --runtime /srv/ds41f-runtime --variant 1.2.7
```

The original 1017 template stays on followers. Model, tokenizer and weight bytes
are preserved. Fill your own topology in the untracked `tensorfold/cluster.local.json`.
Print and inspect commands before adding `--run` on each corresponding host:

Set each node's `root` to its actual installed runtime directory (for example
`/srv/ds41f-runtime` above); the topology example intentionally uses a placeholder
layout and management address.

```sh
python3 -m tensorfold.launch --config tensorfold/cluster.local.json --variant 1.2.7 --rank 0
python3 -m tensorfold.launch --config tensorfold/cluster.local.json --variant 1.2.7 --rank 1
python3 -m tensorfold.launch --config tensorfold/cluster.local.json --variant 1.2.7 --rank 2
```

The launcher validates the exact build receipt, executable hashes, model,
templates, assets and RoPE capacity. A local rebuild needs local serving
qualification; reference hashes identify our deployment, not a guarantee of
bit-identical compiler output on every host.

### NVMe companion and startup

The unchanged production helper is [nvme_keepalive.py](../tensorfold/nvme_keepalive.py).
It observes **native** block-read activity, so its own reads cannot keep the lease
alive. It checks the executable identity, selects allocated extents in the sparse
Engram files, and uses read-only `O_DIRECT`, without changing NVMe APST. Its
isolated process cannot block an inference thread. Unsupported backing storage
fails closed rather than pretending to issue device reads.

For the public service templates, set `TF_PROFILE=1.2.7` in
`/etc/ds41f-tensorfold.env` and your topology in `/etc/ds41f-tensorfold.json`.
Install [tp3@.service](../tensorfold/tp3@.service) and
[tp3-keepalive@.service](../tensorfold/tp3-keepalive@.service), adapting repository
paths. Enable only the local rank on each host. The companion resolves its native
PID and verified build hash through [keepalive_launch.py](../tensorfold/keepalive_launch.py).

Our production installation additionally uses an existing **coordinated recovery
controller**: it waits for all three nodes, assets and RDMA readiness, stops the
whole old native generation, then starts followers and head with boot-bound
permits. It does not reboot machines or restart Hermes. Simple per-rank public
service templates do not provide that full cluster orchestration; operators
must integrate their own cluster supervisor rather than independently restarting
a failed rank into a live old generation. Preserve the 1,800-second peer startup
window and place gateway ingress behind native model and vision-control health.

### Gateway and images

Use the [published gateway](GATEWAY.md) with your own credentials and backend URL.
Its module bytes and vision policy remain those of 1.2.6/5c. Durable jobs retain
finite deadlines, explicit acceptance/cancellation reconciliation and two image
slots. MAX/8K applies to standalone vision; inline agent histories retain their
request budgets. Do not replace those histories with a standalone prompt.
Private diagnostic captures are never publication inputs.
