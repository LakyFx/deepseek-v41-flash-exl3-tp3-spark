# DS41F 1.2.0: DeepSeek V4.1 Flash 1017, EXL3, TensorFold TP3

The model recipe below remains unchanged. For the separately published serving
layer use the [production gateway guide](GATEWAY.md) from `v1.2.1` or current `main`;
the original `v1.2.0` tag predates that gateway update.

**1.2.0 adds the 1017 model revision to the existing native TensorFold recipe.** It uses our independently generated [EXL3 3.5bpw TensorFold weights on Hugging Face](https://huggingface.co/LakyFx/DeepSeek-V4.1-Flash-1017-EXL3-3.5bpw-TensorFold). The existing TensorFold runtime/kernel source is retained. Previous TF351, TF351-3.3M, TF29, C4 / 1.0.0 and X11c variants, results and build inputs remain available.

No new comparative performance or model-quality campaign was run for this release. Existing benchmark tables still describe their original model revisions and settings. The 1017 deployment passed the already recorded functional serving checks linked below; they are not new benchmark scores.

## Prepare the unchanged runtime

Obtain this recipe version:

```sh
git clone https://github.com/LakyFx/deepseek-v41-flash-exl3-tp3-spark.git
cd deepseek-v41-flash-exl3-tp3-spark
git checkout v1.2.1
```

Use a new runtime root, for example `/srv/ds41f-1.2.0`, and retain the previous trees for rollback. From this repository, follow [TensorFold installation steps 1 and 2](TENSORFOLD-INSTALL.md#1-extract-the-pinned-source-and-kernels) to extract and build the native head **and** `tf-dsv41-lanes`, using a separate build output such as `/srv/ds41f-1.2.0-build`. Keep the existing GB10/SM121 host, CUDA/RDMA/NCCL requirements.

Generate the matching kit with [the existing RoPE procedure](TENSORFOLD-INSTALL.md#5-generate-the-matching-rope-kit), retaining `--pool 10000000` for the **table generation**:

```sh
python3 tensorfold/make_rope.py \
  --reference /srv/ds41f-1.2.0-build/reference \
  --kit /srv/ds41f-1.2.0-build/kit --pool 10000000
```

Distribute the resulting complete `kit/` and both executables under each node's new `bin/`. Reusing the same already verified production kit is also valid. A clean build can have different executable hashes from the historical production binary; it still needs operator acceptance on the destination cluster. This publication does not claim a new build/load test.

Include `kit/engram-token-map.json` from the public extraction. Its bytes match the map used by the running 1017 deployment. If reusing a production kit whose token map lived in a separate directory, supply that matching map inside the new kit as expected by the public launcher.

**For 1.2.0, replace the old checkpoint download/export/Engram steps 3, 4 and 6 with the prebuilt 1017 downloads below.** Do not populate this variant from the older Pollard/Mia checkpoint bytes or reuse old Engram data. The shared engine/kernel/RoPE assets are retained; all model weight values come from the pinned 1017 base.

## Download one rank per Spark

Install the Hugging Face CLI in your preparation environment. On each node, set its real rank and download into the new runtime root. These commands do not start the model:

```sh
ROOT=/srv/ds41f-1.2.0
RANK=0  # set to this node's rank: 0, 1 or 2
REPO=LakyFx/DeepSeek-V4.1-Flash-1017-EXL3-3.5bpw-TensorFold
HF_REV=8621801c1fc74aece1fa83e67c6ade3fde1e7894

hf download "$REPO" --revision "$HF_REV" --local-dir "$ROOT/weights" \
  --include 'models/TF351-1017/*' \
  "rank-cache/TF351-1017/rank${RANK}of3.*" \
  "engram-tp3/rank${RANK}.sparse.tar" \
  "engram-tp3/rank${RANK}/SOURCE.json" \
  'RELEASE-MANIFEST.json' 'RELEASE-LAYOUT.md' 'verification/*'
```

Before extracting or loading, check the downloaded files against the pinned `RELEASE-MANIFEST.json`. This performs full local file reads, including the large rank binary and archive, and is preparation work rather than a serving benchmark:

```sh
python3 - "$ROOT/weights" "$RANK" <<'PY'
import hashlib, json, pathlib, sys
root = pathlib.Path(sys.argv[1]); rank = int(sys.argv[2])
manifest = json.loads((root / 'RELEASE-MANIFEST.json').read_text())
assert manifest['status'] == 'READY_TP3_GPU_SMOKE_VERIFIED'
assert manifest['source_revision'] == '1bae0e1088993b9b82de08f59de5be5a34e42170'
records = {row['path']: row for row in manifest['files']}
names = [name for name in records if name.startswith('models/TF351-1017/')]
names += [f'rank-cache/TF351-1017/rank{rank}of3{suffix}'
          for suffix in ('.bin', '.receipt.json', '.verified.json')]
names += [f'engram-tp3/rank{rank}.sparse.tar', f'engram-tp3/rank{rank}/SOURCE.json']
for name in names:
    path = root / name; expected = records[name]
    assert path.stat().st_size == expected['bytes'], name
    with path.open('rb') as stream:
        assert hashlib.file_digest(stream, 'sha256').hexdigest() == expected['sha256'], name
print('Downloaded 1017 rank and wrapper SHA-256 checks passed')
PY
```

Each Engram archive is approximately 67.6 GB and expands to sparse files with approximately 203 GB of logical extent but about 67.6 GB of allocated data. Extract only the matching rank using **GNU tar**, and preserve holes on later transfers:

```sh
tar --sparse -xf "$ROOT/weights/engram-tp3/rank${RANK}.sparse.tar" \
  -C "$ROOT/weights/engram-tp3" --strip-components=1
cmp "$ROOT/weights/engram-tp3/SOURCE.json" \
  "$ROOT/weights/engram-tp3/rank${RANK}/SOURCE.json"
```

Never extract multiple ranks over each other in a shared directory. Budget space for both the archive and extracted data, the approximately 85.9 GB rank binary, wrapper, runtime kit and rollback tree.

The pinned native reader requires a **regular `rankNof3-*.bin` file**, not the bare published filename or a symbolic link. Create a same-directory hardlink without duplicating the weight allocation:

```sh
CACHE_DIR="$ROOT/weights/rank-cache/TF351-1017"
CACHE="$CACHE_DIR/rank${RANK}of3.bin"
ALIAS="$CACHE_DIR/rank${RANK}of3-1017-eb0abe4d9d54.bin"
if [ -e "$ALIAS" ]; then
  test "$CACHE" -ef "$ALIAS" || exit 1
else
  ln "$CACHE" "$ALIAS"
fi
test ! -L "$ALIAS" && test "$CACHE" -ef "$ALIAS" || exit 1
```

There must be exactly one discoverable regular `rankNof3-*.bin` for the node. Include the published `chat_template.jinja` sidecar; the canonical 1017 tokenizer config intentionally remains unchanged. The sidecar passed 56 comparisons against the frozen 1017 reference encoder.

The final local tree is:

```text
/srv/ds41f-1.2.0/
  bin/tensorfold-native
  bin/tf-dsv41-lanes
  kit/                                  # complete retained 10M RoPE + repaired AOT kit
  weights/models/TF351-1017/             # config, tokenizer, chat template, vision, receipts
  weights/rank-cache/TF351-1017/         # this rank's binary, regular hardlink, receipts
  weights/engram-tp3/                    # this rank's SOURCE.json and two sparse table files
```

## Select and launch the new variant

Copy `tensorfold/cluster.example.json` to the untracked `tensorfold/cluster.local.json`. Set all three `root` values to the new runtime root on the corresponding nodes and fill your actual topology as in [the existing topology procedure](TENSORFOLD-INSTALL.md#8-topology-print-and-launch). Keep the four-rail order, peer masks and GID choices explicit; example addresses and NIC placeholders cannot start a rank.

Print the commands first:

```sh
python3 tensorfold/launch.py --config tensorfold/cluster.local.json --variant 1.2.0 --rank 0
python3 tensorfold/launch.py --config tensorfold/cluster.local.json --variant 1.2.0 --rank 1
python3 tensorfold/launch.py --config tensorfold/cluster.local.json --variant 1.2.0 --rank 2
```

Add `--run` only on the corresponding node after preparation and in an operator-controlled switch window. The launcher checks the new arm/source revision, chat-template hash, Engram rank/source/file sizes, unique regular cache hardlink, model assets and RoPE lengths. Full payload SHA verification is the preparation step above. The generic service template can select `TF_PROFILE=1.2.0` when the operator installs it; this release does not change running services or persistent boot selections.

Retain the API alias `deepseek-v4.1-flash`. The separate gateway observed with this deployment used concurrency 12 and admission budget 5,336,064; this is distinct from the native 8M KV pool and is not configured by the rank launcher. Gateway authentication and routing remain operator-owned. Keep cross-revision KV caches separate. Rollback uses the retained old model, Engram, launcher selection and gateway settings as a coordinated three-rank switch.
