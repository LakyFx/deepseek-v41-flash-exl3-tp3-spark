# DS41F 1.2.3: the measured xTF recipe, released

**1.2.3 is the release name of 1.2.2xTF**, with no new model or performance
claim created by the rename. It is DeepSeek V4.1 Flash 1017 on TensorFold TP3,
C12 / R48 / 7M KV / 3 GiB snapshot cache, with online cost and acceptance
learning. The matching gateway remains C12 with two concurrent vision jobs;
further accepted image jobs queue. Text uses MAX and vision uses MEDIUM.

Read the [complete benchmark report](WORKFLOW-BENCHMARK-20261020.md),
[learner design and AdaSpark attribution](ADAPTIVE-SPECULATION.md),
[numeric evidence](../results/20261020-adaptive/) and
[34-page PDF](../results/20261020-adaptive/workflow-report-reproducibility.pdf).
The [benchmark settings addendum](BENCHMARK-SETTINGS-20261020.md) identifies
the exact checkpoint, quantized weights and effective sampling in all three arms.
All previous engine variants and historical measurements remain available.

## Exact configuration and changes

| Item | 1.2.2TF original | Bert1 experiment | 1.2.3, measured as 1.2.2xTF |
|---|---:|---:|---:|
| Native serving slots | 12 | 16 | 12 |
| Shared verification-row ceiling | 32 | 48 | 48 |
| Logical KV pool, tokens | 8,000,000 | 7,000,000 | 7,000,000 |
| Head prompt-state snapshot cache | 2 GiB | 2 GiB | 3 GiB |
| Gateway reserved-token ceiling | 5,336,064 | 6,699,008 | 5,336,064 |
| Speculative allocator | Original cost-based | Original cost-based | Online calibrated cost + acceptance |

R is the total verification row budget, including mandatory rows, not a draft
length per request. Gateway ceilings were not exercised by the direct-native
benchmark. The 7M configured pool was not filled to saturation by that short
workflow. Snapshot cache capacity is separate from the logical KV pool.

Weights, the source model revision, tokenizer/template, Engram, quantization,
target verifier, sampler, TP3 CUDA/RDMA paths and 2,200 MHz GPU clock are retained.
The [profile](../tensorfold/profiles/1.2.3.json) retains the pinned
`LakyFx/DeepSeek-V4.1-Flash-1017-EXL3-3.5bpw-TensorFold` revision from 1.2.0.
Approximately 3.51 bpw describes routed experts; the whole model is mixed
precision. Request context remains 401,408 tokens.

## Build the additive native overlay

Prepare a new runtime/build tree; keep earlier binaries and caches for rollback.
This procedure does not stop a service, load a model or start a GPU benchmark.

```sh
git clone https://github.com/LakyFx/deepseek-v41-flash-exl3-tp3-spark.git
cd deepseek-v41-flash-exl3-tp3-spark
git checkout v1.2.3

python3 tensorfold/extract.py --out /srv/ds41f-1.2.3-build
python3 tensorfold/adaptive/build.py \
  --build-root /srv/ds41f-1.2.3-build \
  --out /srv/ds41f-1.2.3-built --zig /path/to/zig
```

Use Zig 0.17.0 and the existing [TensorFold host/build requirements](TENSORFOLD-INSTALL.md).
The wrapper applies the exact measured patch, runs the module/full-native/CPU
overhead tests, and builds `native` plus `dsv41-tools` for aarch64. Its input is
the new extractor output; it refuses a drifted or already-patched base.
`--prepare-only` verifies only the generated source and performs no compilation.

The measured candidate passed 322 full native CPU tests before the GPU workflow
campaign. Rebuilding on another host creates a new build receipt, not a claim
that that host has already passed a GPU acceptance run.

Install the two binaries and receipt into the new runtime root on each rank:

```sh
python3 - <<'PY'
import json, pathlib, shutil
built = pathlib.Path('/srv/ds41f-1.2.3-built')
dest = pathlib.Path('/srv/ds41f-1.2.3/bin-1.2.3')
dest.mkdir(parents=True, exist_ok=False)
receipt = json.loads((built/'BUILD.json').read_text())
for name, record in receipt['binaries'].items():
    shutil.copy2(built/record['path'], dest/name)
shutil.copy2(built/'BUILD.json', dest/'BUILD.json')
PY
```

This separate `bin-1.2.3/` directory avoids silently selecting the old engine.
The launcher checks source/overlay identities and both installed binary hashes
against this receipt when `--run` is requested. This catches an accidental old
binary plus a new environment flag; it is not a security signature.

## Prepare the same 1017 assets and launch

Follow the [1.2.0 pinned weight download and local rank/Engram preparation](DS41F-1.2.0.md),
using `/srv/ds41f-1.2.3` as your new runtime root. Do not redo the older
Pollard/Mia conversion for this variant. Retain the same kit, token map,
checksum-verified RoPE tables, sparse Engram ownership and hardlink discovery
contract. The existing 10M-extent RoPE tables cover the configured 7M pool;
their file extent is not the active KV capacity. Model weights are not in Git.

Copy `tensorfold/cluster.example.json` to your private `cluster.local.json`,
then provide your actual roots, management topology, HCA names, GID indices,
NCCL subnet/interface and library path. Do not copy our private addresses.
Inspect all three commands before starting anything:

```sh
python3 tensorfold/launch.py --config tensorfold/cluster.local.json --variant 1.2.3 --rank 0
python3 tensorfold/launch.py --config tensorfold/cluster.local.json --variant 1.2.3 --rank 1
python3 tensorfold/launch.py --config tensorfold/cluster.local.json --variant 1.2.3 --rank 2
```

Add `--run` only for your intended deployment. It sets
`TF_DS_ADAPTIVE_LEARNING=1` on every rank. Keep all ranks coordinated; selecting
only one new binary does not form a valid TP3 deployment. Check actual native
health and readiness before admitting traffic. New-host acceptance remains
your own measurement; the recipe never restarts another named service.

For persistent startup use the explicit
[`tp3@.service`](../tensorfold/tp3@.service) template with the 1.2.3 selector
(`TF_PROFILE=1.2.3` in `/etc/ds41f-tensorfold.env`) and your actual paths.
It waits/retries through the existing native startup
policy; configure your network/storage readiness and preserve the previous
unit for rollback. The learner is process-local and restarts from priors.

## Gateway and vision

Install the [gateway package](GATEWAY.md) at version 1.2.3 in a separate venv
with your own secret, upstream, TLS/topology and private durable state.
Its nonsecret production policy stays C12 / 5,336,064 admission tokens, MAX

the existing 900-second image-job deadline including queue time.

This publication includes the already deployed repetitive-vision-output drain
fix: finish reading the owned backend response before reporting validation
failure, preserving the no-automatic-replay rule for unknown dispatches.
The deduplication identity revision is retained across this compatible update.
These are existing production settings/fixes, not new vision throughput
results. The workflow benchmark below contained no image requests.

## Measured result and limits

Across 78 tasks per recipe, all three recipes eventually completed 78/78.
Summed measured wave time was 22:27.872 for original TF, 23:38.938 for Bert1,
and 20:29.795 for xTF: 8.76% less than TF and 13.33% less than Bert1.
Intermediate rejected tool attempts were 30 / 31 / 16. xTF also emitted
6.69% fewer tokens than TF, so the full wall-time gain cannot be assigned
to engine speed alone. At C6, median native per-request decode was 25.82
tok/s vs TF's 23.34; at C12 it was slightly lower (14.09 vs 14.65).

One matched-initial-input pass is not a statistical quality result. The test
does not isolate R48, cache size, KV capacity or online learning; it does not
validate long-session repetition resistance, full pool saturation, mixed
vision/text contention, or hours-long production reliability. The
[complete report](WORKFLOW-BENCHMARK-20261020.md) retains counterexamples,
latency scope, partial-attempt provenance and all measured cells.
