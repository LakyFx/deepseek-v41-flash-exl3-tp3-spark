# DS41F 1.0.0 is C4

**DS41F 1.0.0 is the C4 variant measured in the October 11–12 campaign and selected for production on October 12.** It is not a new model, new quantization, or an unmeasured combination built after the campaign. The internal compatibility label remains `0.8.9X11c-C4`; logs carrying that label identify the same recipe.

The objective is sustained Hermes agent work with long inputs, reusable prefixes and MAX reasoning. We retained the checkpoint and approximately 3.3M-token KV pool. We did not switch to NVFP4, TensorFold, expert parallelism or a different trained Markov rank.

CUDA remains from the pinned CUDA 13 base. The host migration required a loader compatibility change, retained in this release, rather than assuming every old overlay would work unchanged.

## What was added to X11c

C4 = **X11c on the qualified 64K-page host + N1 + N2 + N3 + N4 + N6**. The older R/K/D/I1/I2/H/M/P/A modules and bounded X11c prefetch remain included. N5, N7a/b, N8a/b and an additional N9 graph configuration are not part of C4.

### N1: avoid over-shortening C1 verification

Adaptive verification estimates whether checking more drafted tokens will pay for its GPU cost. For exactly one eligible pure-decode request, N1 instead verifies the full valid scheduled proposal, up to K5. It uses request and prefill metadata, not padded graph row count, to select the path. It respects clipped and end-of-sequence proposals. Other regimes retain adaptive verification.

This can save extra target iterations when accepted proposals are useful. It can also waste verification work on rejected proposals. N1 alone was slower than B0 in the measured Hermes C1 cohort, so it is not advertised as a universal single-stream improvement.

### N2: choose the mHC path by real phase and small row count

For 1–6 rows of pure decode, N2 uses the stock lagged mHC path. Mixed batches and prefill retain the fused implementation. Tiny prefill must not replay a graph captured with pure-decode metadata, so that case uses the appropriate eager path. The distinction is necessary for correctness, not just tuning a launch size.

The intended benefit is avoiding fixed fused-path overhead when the batch is very small. N2 alone slightly improved the measured C3 and long prefill results, with essentially unchanged C1/C8. It does not demonstrate that unfused mHC is always faster.

### N3: cheaper draft bookkeeping without changing the sampling distribution

N3 reuses logits scratch storage and batches position-key preparation. Draft weights, probabilistic sampling and rejection policy stay the same. It reduces allocation and host orchestration opportunities rather than increasing the maximum generated draft length or switching to greedy speculation.

Its isolated result was mixed: C3 improved, while C1 and C8 declined. Output token counts and acceptance vary between completed agent workflows; the numerical records retain those denominators.

### N4: specialize the existing EXL3 prefill kernel

The existing kernel already reuses each decoded weight tile. N4 changes the warp layout from eight to four warps for eligible large routed batches at the actual TP3 projection shapes: `(k=5120,n=1536)` and `(k=768,n=5120)`, MUL1 K3/K4, with more than `48 * top_k` valid routed rows. It retains FP32 accumulation and the existing decoder. The small-row K fast path is unchanged.

`CUDA_EXL3_NEXT_PREFILL=1` selects this compiled specialization. Setting that environment variable on the old binary does not install the new kernel. This is why the release includes the matching `gemm.cu` source and rebuilds the extension.

### N6: bounded decoder replay for long prefill

DeepSeek's model geometry allows a reviewed late decoder region to run on a bounded suffix after the required KV-source work has written all rows. This implementation uses cut 20 and the 128-row sliding window, constructs the smaller replay batch, gathers the needed hidden states, runs the late layers with their own attention metadata and scatters the outputs back. It preserves the cache, indexer, late-hidden DSpark and vision contracts.

Large piecewise graphs can break into separately captured inner replay graphs. Full/small graph paths retain their reviewed behavior. Inner sizes are bounded at 128–1,024 rows, with trim threshold 768, to avoid uncontrolled graph/workspace growth. The port includes scheduler, cache, metadata and custom row-partitioning integration; copying only the decoder loop is insufficient.

This is the strongest isolated prefill result in this campaign. N6 achieved 1,770.3 computed tok/s on the Hermes cold 64K phase; C4 achieved 1,734.1 versus B0's 1,318.0. N6 and C4 were also the only two arms to complete the entire bounded 128K-C3 cold/hot phase. Their measured decode results still have tradeoffs.

## Why choose C4

Against the fresh B0 baseline in the same host64k campaign, C4 measured:

| Metric | B0 | C4 / 1.0.0 | Change |
|---|---:|---:|---:|
| Hermes C1 request decode tok/s | 62.3 | 63.6 | about +2.1% |
| Hermes C3 request decode tok/s | 31.2 | 34.1 | about +9.3% |
| Hermes C8 hot aggregate output/wall tok/s | 159.0 | 146.1 | about -8.1% |
| Hermes cold 64K computed prefill tok/s | 1,318.0 | 1,734.1 | about +31.6% |
| Owen code C8 aggregate decode-window tok/s | 192.9 | 194.5 | about +0.8% |
| Owen cold nominal 256K input/TTFT tok/s | 1,230.2 | 1,687.2 | about +37.2% |

The full precision values, individual repeats and all variants are in [CAMPAIGN-20261012.md](CAMPAIGN-20261012.md). C4 was selected for the long-context/prefill behavior and useful concurrent work, not because every number is the largest. The original targets of Hermes C1 70+ and C8 180+ were not both reached. Owen's 194.5 C8 uses a different workload and denominator and cannot be substituted for Hermes C8.

The campaign temporarily finished on C5-sp256 before the owner selected C4. That temporary end-of-test state is not the production release choice. Older documents describing X11c as selected refer to the earlier October 9 decision.
